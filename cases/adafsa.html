The short version

From inconsistent screens to a shared language

The problem

Every new TAMM service was built from scratch. Nobody had documented the patterns that already existed: three versions of the same input, status labels with different meanings, and RTL as an afterthought.

What I did

Audited, tokenised, aligned and documented. From an inventory of every screen to a four-layer component library in Figma, with RTL designed in from the start.

The outcome

A shared language for designers and developers. 20 components and 87 variants, each with usage guidance, so handoffs no longer had to be conversations.

Context

The situation I walked into

ADAFSA manages agricultural licensing, livestock management, food safety and fodder subsidies for Abu Dhabi's farming community, all through the UAE's TAMM government platform.

My position

Designer from Capgemini, embedded within the ADAFSA product team alongside two client-side designers.

The setup

Three designers total. Approval and sign-off happened client-side. My job was to propose, justify and build.

What existed

Working screens. Real users. No underlying system, no documentation, no shared language between design and dev.

Many users are farmers with limited digital experience, using the platform in Arabic to submit monthly livestock reports, request subsidised fodder and track applications.

What existed

The screens worked, but every service was built from scratch

Nobody had documented what patterns already existed. The result:

  • Three different implementations of the same form input
  • Status labels that meant different things on different pages
  • Arabic RTL layouts applied as an afterthought on some screens, and ignored on others

The problem

Three problems, one root cause

01

Inconsistent UI across services

The same number stepper had three different visual implementations. Status indicators used different colours and labels for identical states.

02

No documentation or handoff process

No component documentation, no token naming, no usage guidance. Developers were eyeballing designs. Every handoff was a conversation.

03

RTL Arabic support was broken

Arabic layouts were added reactively. Inputs, the process stepper and navigation didn't mirror correctly, in a service used mostly by Arabic speakers.

Root causeThere was no shared design language. Every designer and developer was working from memory and personal interpretation.

The hard part

I had to make the case for system thinking without the authority to mandate it.

Two client-side designers had existing opinions about how things should look, and developers needed clarity to build. Every decision needed to be collaborative and well-reasoned.

My process

How I approached building the system

I didn't start by designing new things. The goal was to document and systematise reality, not impose a new aesthetic.

1 · Audit

Inventory every screen and pattern

Catalogued every button, input and status indicator across ADAFSA's TAMM services: 20 component types, 87 variants.

2 · Extract

Pull out the underlying tokens

Mapped every hardcoded colour, spacing unit and font size to a named token. 34 hex values became 9 semantic tokens.

3 · Align

Get the client team on the same page

Showed the two client designers the inconsistencies side by side, then agreed the canonical version of each component together.

4 · Build

Design the component library

Tokens, base components, composites, page templates. Every state built, with RTL variants alongside LTR, not after.

5 · Document

Write usage guidance for every component

What it's for, when to use it, when not to, its tokens and its RTL behaviour. The most time-consuming part.

Before and after

What I found, and what I delivered

What I found
  • 3 different number stepper implementations with inconsistent behaviour
  • 34 unique colour values with no naming or grouping
  • 5 different status labels used interchangeably for the same states
  • RTL applied reactively, breaking the process stepper and form inputs
  • No component documentation: every handoff was a conversation
  • Developers rebuilding components from scratch for each new service
What I delivered
  • 1 canonical number stepper: specified, documented, RTL-ready
  • 9 semantic colour tokens covering every use case
  • 4 named status states with clear definitions and usage rules
  • RTL built structurally into every component from the start
  • A full component library with usage guidance for every component
  • 20 components, 87 variants: a shared language for the whole team

My contribution

My contribution

I wasn't there to redesign the product. I was there to give the team a shared language, so every designer and every developer could make consistent decisions without needing to ask.

System thinking

Identified the underlying token structure, named it, and made it the foundation everything else referenced.

Collaboration

Worked across Capgemini and ADAFSA teams: proposing, justifying and aligning rather than dictating.

Documentation

Wrote the component documentation and usage guidance the team had never had, making the system usable, not just deliverable.

Reflection

What I learned

01

Systems work is political, not just technical.

Getting two client-side designers to adopt a shared system meant showing, not telling. The audit made the case in a way arguments couldn't. Make problems visible before proposing solutions.

02

RTL is a design decision, not a dev task.

Arabic support fails when designers treat it as a developer concern. Every component has to be conceived bidirectionally. I now design with logical properties in mind from the first frame.

03

Naming is design.

Standardising the four status states had as much user impact as any visual change. Good naming reduces user confusion without changing a single pixel.

04

Not measuring outcomes is a gap to close.

The team's feedback was that builds became faster and more consistent once the library existed. We never instrumented that. Next time I'd set success criteria at the start, so the outcome is shown with evidence and not only feedback.
